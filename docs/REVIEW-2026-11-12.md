## 1. Blocking corrections

These must be fixed before the plan is used as the spec.

**BC1. The "frozen 85" surface omits `G`, `gg`, `r` (and IV's `ge`/`gE`).**
`build_matrix.py:187-210` (`FAMILIES`) has no row for `G`, `g` or `r`. Yet busybox implements
all three (active cases, `vi.c` `case 'g'`, `case 'G'`, `case 'r'`), and IV's curated map has them
(`build_matrix.py:104,112`). They appear in neither the tally nor the 85. `<count>` and `:` *are*
counted as "commands". Re-running the generator gives 64 + 10 + 6 + 4 + 1 = 85, which confirms
the arithmetic but not the coverage. **Correct statement:** the intended surface is about 88
commands (85 − `<count>` + `G` + `gg` + `r`), plus a ruling on `ge`/`gE`, which IV supports
(`key-parser.js:178-184`) and busybox does not.

**BC2. `^R` "host owns it" deletes redo and, on Chrome, reloads the page.**
The matrix classes `^R` as busybox's *redraw* (`THREE-WAY-MATRIX.md:128`; `HOST_OWNED`,
`build_matrix.py:319`). IV binds `^R` to **redo** (`event-interceptor.js:614-622`). busybox has
no redo, and nvi's `u` toggles. If `^R` passes through, NORMAL-mode Ctrl+R in a Chrome tab is a
page reload, which loses the prompt. **Correct:** `^R` = redo (Vim lineage) belongs in the
`BEYOND` set next to `v`, `V`, `*` and `#`.

**BC3. The three oracles disagree on core semantics, and the plan names no tie-breaker.**
Measured with `x x u u` (probe `drive.py`):
- `vim -u NONE` runs in **'compatible' mode**: `uu` = undo then redo (vi toggle).
- `vim -u NONE -N`: both changes are undone.
- `nvi`: toggles.
- `busybox`: multi-level, and has no redo.

`ENGINE-DECISION.md:138` and the escape-hatch launch line (`THREE-WAY-MATRIX.md:330,356`) both say
`vim -u NONE`, i.e. compatible mode. That is probably not what you meant for either use. **Correct:**
the matrix needs an **"oracle of record" column**. Recommendation: busybox decides **scope**;
`vim --clean -N` with pinned `cpoptions`/`joinspaces` decides **semantics**. nvi and busybox diffs
are informational, not normative.

**BC4. "`:s` — JS `RegExp` covers it" is false, and busybox-parity `:s` surprises vi users.**
Measured (probe `drive3.py`):

| Case | busybox | nvi | vim -N | JS `RegExp` (by spec) |
|---|---|---|---|---|
| `s/one/[&]/` | `[&]` (literal) | `[one]` | `[one]` | depends on translator |
| `s/\(o\|on\)/X/` on `one` | `Xe` (POSIX leftmost-*longest*) | no match (no `\|`) | `Xne` (leftmost-*first*) | `Xne` |
| `s/[[:space:]]/_/` | matches space | wrong match | matches space | **no match**: `[[:space:]` + literal `]` |

**Correct:** `:s` needs a BRE→JS **translator with an explicit refuse list**, not "JS RegExp
covers it". The translator handles escaping of `( ) { } + ? |`, `\(`, `\{m,n\}`, `\<`, `\>`,
POSIX classes, and a function replacer so a `$` in user text is never interpreted. You also need a
ruling on `&`: busybox makes it literal; every other vi makes it the match.

**BC5. The three "reuse as-is" adapters are bound to the engine being deleted.**
`ENGINE-DECISION.md:106` says to reuse `vscode-input-vim.js`, `chat-webview-input-vim.js` and
`prosemirror-input-vim.js` as-is. All three construct `new IV.InputHandler()` and
`new IV.VimEngine()` and call `handler.execute(draft, …)` on a fake `{tagName:'INPUT', value,
selectionStart…}` object:
- `vscode-input-vim.js:80-99`, `:304-306`
- `chat-webview-input-vim.js:150-151`, `:253`
- `prosemirror-input-vim.js:145`, `:293`, `:402-404`

**Correct:** they must be re-pointed at the new engine. The useful consequence is that their
`snapshot()` → `execute` → prefix/suffix-diff `commit()` pattern (`vscode-input-vim.js:83-130`)
**is already the adapter contract**. Extract it from them, not from the IV handlers.

**BC6. "event-interceptor: keep unchanged (… IME and Esc handling)" is false.**
`ENGINE-DECISION.md:104`:
- There is **no IME handling** in IV's `content/`. `grep` finds no `isComposing`, no
  `composition*` and no keyCode 229. The IME handling lives only in the host-side adapters
  (`vscode-input-vim.js:202,290-295`; `prosemirror-input-vim.js:302,385-389`;
  `chat-webview-input-vim.js:301,377-380`).
- The interceptor drops every ctrl combo except `^R ^V ^D ^U` and insert-mode `^W`
  (`event-interceptor.js:614-679`). Adding `^B ^E ^F ^Y ^G ^H ^J ^N ^P` means editing it.
- It contains editing code (`:68-440`) and an async-paste path that **reorders keystrokes**:
  `p` waits on `navigator.clipboard.readText()` while the following keys run synchronously
  (`:867-875`).

**Correct:** about half of `event-interceptor.js` changes. Budget it.

**BC7. The `:e` transport, as written, fails on both the Chrome path and most Electron composer hosts.**
- Chrome: a content-script `fetch` carries the **page** origin and is CORS-bound ("Content
  scripts initiate requests on behalf of the web origin…", Chrome docs, *Cross-origin network
  requests*). Your suspicion is correct. Only the service worker or extension pages send
  `Origin: chrome-extension://`. Chrome also terminates an extension service worker "when a
  `fetch()` response takes more than 30 seconds to arrive" (Chrome docs, *Extension service
  worker lifecycle*). The TextEditAid model of **holding the POST open until the editor exits
  therefore breaks for any edit longer than 30 s.** TextEditAid itself (`background.js`) has this
  exposure.
- Electron composers: CSP **blocks loopback** in VS Code chat (`vscode.md:59`), Cursor Molten
  Agent (`webview-coverage.md:51`) and Devin `sessions.html` (`README.md:163-166`; it *does*
  allow `ws:`). The plan's "degrade to clipboard" row (`THREE-WAY-MATRIX.md:294`) is therefore
  the **main path** on the primary targets, not an edge case.
- Token design is internally inconsistent. "Token generated fresh at daemon start"
  (`THREE-WAY-MATRIX.md:346-347`) cannot reach a page-world payload without an unauthenticated
  delivery channel. A token baked in at patch time sits in a world-readable app bundle and in a
  JS variable the page realm can read. `fetch` can be monkey-patched. See B6.

**BC8. `+{line}:{col}` is not valid vim syntax, and the editor needs a terminal.**
`THREE-WAY-MATRIX.md:305-307` is wrong in four ways:
- `+N` takes a line or an Ex command, so `+12:5` is not a line-and-column jump. Use
  `-c 'call cursor(L, C)'`.
- `col('.')` returns **bytes**, while JS offsets are UTF-16. Use `charcol('.')` and convert in
  the daemon.
- A daemon has no tty. `vim` must be launched inside a terminal emulator **that blocks until
  exit**. `gnome-terminal` forks and returns at once, which would end the session immediately with
  the text unchanged. Alternatively use `gvim -f`, which is what TextEditAid does with `rgvim -f`.
- `'fixeol'` appends a trailing `\n` on every round trip. TextEditAid has a `strip` option for
  exactly this.

**BC9. The documents contradict each other; "the matrix wins" (`FEATURE-MATRIX.md:7-10`) does not resolve it.**
- `THREE-WAY-MATRIX.md:36-37` still lists `H M L z` and the scroll keys as excluded, while its own
  table and §Viewport put them in the baseline.
- `FEATURE-MATRIX.md:109-129` (§3) still credits busybox with `( ) [ ] * @ v V S ! = K Q \`,
  directly under its own correction note (`:97-105`).
- `FEATURE-MATRIX.md:40-43` and `:210-212` say visual mode is "referenced by busybox".
- §8 (`:230-245`) says no marks, no registers, no `:` commands and "native host history". This
  contradicts both the ruling and `ENGINE-DECISION.md:90` ("undo via an op log").
- The matrix note for `&` (`THREE-WAY-MATRIX.md:182`, `build_matrix.py:310`) says "`:s` depends
  on ex mode — out", but `:s` is now in.
- "Support columns are parsed, not recalled" (`THREE-WAY-MATRIX.md:3-4`) is false for the IV
  column, which is a hand-curated dict (`build_matrix.py:96-120`).
- `input-vim-surface.txt:6-7,10` is mis-extracted: `"->SINGLE_QUOTE`, `CHAR_PAIR_KEYS` echoes
  `MOTION_KEYS`, and "handler case labels" is empty (`extract.py:109-117` regex).
- `FEATURE-MATRIX.md:18` says Debian nvi is built from the nvi2 lineage. It is not:
  `dpkg -s nvi` gives `Homepage: https://repo.or.cz/nvi.git`, a sibling fork. The spec source and
  the oracle binary differ. busybox has the same split: master source with regex off by default,
  but Debian 1.38.0 with regex on.

## 3. Missed items, ordered by how expensive they are to discover late

1. **Contract offsets: unit and versioning.** See risks 4 and 5. The plan's
   `getBuffer() -> {text, lines, cursor}` (`ENGINE-DECISION.md:119-125`) has no `version`, no
   `baseVersion`, no unit definition and no inline atoms. All three are interface-level and
   expensive to add later.

2. **Edit rejection and rollback.** The adapter must be able to refuse an edit: schema forbids a
   sibling item, `filterTransaction`, read-only, or a stale version. The engine must then roll back
   the cursor, the register write, the `.` record, the mark mapping and the `U` snapshot. Neither
   document mentions rejection.

3. **Insert-mode ownership is a design decision, not a detail.** The following assume the engine
   sees inserted text: `R` (busybox replace mode, `vi.c:3725-3741`), `.` on insert commands,
   `:set ai` (applies on `o`/`O`, `vi.c:4282-4292`), `et` (`>`/`<`) and `sm` (showmatch is
   insert-only). Today insert mode is host-owned everywhere. Rule per item: `ai`/`et` apply to
   engine-performed edits only, `sm` is host-owned, and `R` intercepts printable keys only outside
   composition.

4. **IME.**
   - In NORMAL mode with fcitx/ibus active, the IME eats `j` before the page sees it (keyCode 229).
     No browser API toggles IME. The adapters reset to INSERT on composition (`vscode.md:46`), so
     NORMAL mode is effectively unusable with a CJK IME on.
   - `f`/`t`/`r` with a CJK target need composition.
   - The `/` and `:` prompts are a fake overlay fed by `keydown` with `e.key.length === 1` and no
     ctrl/meta (`event-interceptor.js:559,607`). They cannot take IME input, paste, cursor
     movement, or `^R` register insertion. With `:s` in scope this matters.
   - Esc during composition cancels the composition in the IME and must not switch mode.

   Decide early: a real `<input>` in the closed shadow root (which brings focus juggling against
   the hosts' blur handlers), or a documented ASCII-only prompt.

5. **`:e` field identity and apply-while-unfocused.** Vim takes focus, so the host field blurs,
   the focus manager deactivates, and React or Slate may re-mount the node. Two consequences:
   - On return the result needs a stable adapter key rather than an element reference.
   - `execCommand`-based adapters need focus plus a selection to apply.

   If the tab is gone, keep the temp file and print its path.

6. **CAS false positives on `:e`.** Hosts normalise text asynchronously: NBSP↔space in
   contenteditable, CRLF, trailing whitespace, draft sync from another window. Compare
   *normalised* text. On conflict, put the vim result in a register (for example `"e`) and keep
   the temp file. See C5 for the merge path.

7. **Oracle harness specifics.** This was measured, not theorised.
   - nvi and busybox have no `:normal` and no scriptin, so **a pty is required**. Vim can use
     `-s scriptin` or `-es` + `:exe "norm! …"`, but `-es` has no screen, so viewport rows are
     meaningless there.
   - **Esc timing is a nondeterminism source.** busybox gave a different result for the same key
     string in burst versus paced writes (`one §wo three` vs `one §two three`), because ESC plus
     the next key parsed as one sequence. Pace ESC (or set nvi `escapetime`) and always write ESC
     on its own.
   - Set `TIOCSWINSZ`, otherwise busybox sends `ESC[6n` and waits (`FEATURE_VI_ASK_TERMINAL`).
   - Isolate `HOME`, `EXINIT`, `NEXINIT`, `~/.exrc` and `~/.nexrc`. busybox reads `EXINIT` and
     `~/.exrc` (`vi.c:5002-5029`).
   - Pin `LANG`/`LC_ALL`. This machine's locale is zh_CN, and busybox's Unicode handling is
     locale-dependent.
   - Observable after exit: the buffer, plus the cursor via an inserted marker (`<Esc>i§<Esc>:wq`
     works in all three). Not observable: mode, messages and the status line. Those need screen
     scraping (e.g. `pyte`) or are untestable.

8. **Register scope and clipboard regression.**
   - IV defaults to `useClipboard: true` (`settings-manager.js:13`) and mirrors yanks to the
     system clipboard (`register.js:16`). Deferring clipboard mirroring (`FEATURE-MATRIX.md:189-192`)
     is a **regression** for Chrome users.
   - Content scripts run per frame (`all_frames: true`, `manifest.json:27,51`), so in-engine
     registers do not cross iframes, tabs or Electron windows.

   Decide the scope and the async story together.

9. **Viewport tests need a geometry-equivalent fixture, and the oracles disagree anyway.**
   - busybox `^F` = `rows-2` and `^D` = `(rows-2)/2` (`vi.c:3800-3812`). Vim's `scroll` option
     and nvi's values differ.
   - The only way to diff against an oracle is a monospace `textarea` of 80 columns by 22 rows
     with a fixed line-height, so that it matches a 24x80 terminal minus the status line.
   - Rich-editor viewport commands (PM, Slate, Lark, Monaco) can only be tested in each real
     host. That makes "120 LOC + 30 per adapter" (`THREE-WAY-MATRIX.md:256`) optimistic for the
     rich adapters.

10. **busybox quirks a faithful port would import.**
    - Marks are raw pointers and are **not adjusted** on edits. busybox's own comment says so:
      "this is really stupid… could be off by many lines" (`vi.c:3907-3910`).
    - `''` (previous-context swap, `vi.c:3895-3901`) is not in the plan.
    - After `p`, busybox calls `dot_skip_over_ws()` (`vi.c:3956`), which is not where Vim leaves
      the cursor.
    - The `:sort`-as-`:s` dispatch (A7).

    List the quirks you are deliberately *not* porting.

11. **Text objects without an oracle.** `ie`/`ae` (whole buffer) and `i|` `i*` `i/` `i\`
    (`key-parser.js:10-24`) are not Vim built-ins (they come from plugins like textobj-entire and
    targets.vim). "Every behaviour traceable to an oracle case" (`ENGINE-DECISION.md:110`) cannot
    hold for them. Mark them "spec = our tests".

12. **Prompt-text logging.** IV logs the whole prompt on every command
    (`input-handler.js:165`, `val: text`; 29 `console.log` across the handlers), stripped only in
    the local canonical copy (`engine-upgrade-2026-10-31.md:45-48`). Put "no prompt text in
    logs or diagnostics" into the engine contract, as the adapters already do (`vscode.md:59`).

13. **Lark is not Electron** (`README.md:100`: ByteDance native shell with embedded Chromium and
    no extension subsystem). "6 Electron apps" should read "6 Chromium hosts". This matters
    because no Electron main-process seam exists there.

## 4. Decision challenges (Task C)

**C1. Is "busybox baseline" the right frame?** It is right as a **scope filter**. It is wrong as
a **behaviour spec**.
- busybox has no visual mode, no text objects, no `*` and no redo. In a chat box, `ciw`, `ci"`,
  `vip`, `V` and `^R` are the most used commands, and busybox says nothing about them.
- Where busybox *does* speak, a literal port is worse than what the 85 implies:
  - `&` is literal in `:s`.
  - Regex is leftmost-longest POSIX, which JS cannot reproduce anyway.
  - Marks drift.
  - Word classes are ASCII.
  - `u` has no redo.
  - `:set` has the `flash` name and no `ts` story.
  - Cursor placement after `p` differs from Vim.
- Users' muscle memory is Vim, and the study already keeps Vim-lineage items (`BEYOND`,
  `build_matrix.py:324`).

**Change:** "busybox decides *whether*, Vim decides *how*". Add an `oracle of record` column and
let busybox and nvi diverge where Vim is canonical.

**C2. Is "rewrite, not patch" sound, and is 1x vs 2x real?** The verdict holds. The argument
does not.
- The 2x is **rhetorical** for the hosts that matter most. VS Code chat, Claude, Codex and Cursor
  Agent already run **only `InputHandler`**, headless, on a plain-object snapshot (BC5).
  `ContentEditableHandler` is used only by the generic content-script gate.
- A patch that (a) retires `ContentEditableHandler` by routing generic contenteditable through a
  snapshot adapter like `chat-webview-input-vim.js`, (b) drops vLines from motions, and (c) adds
  features to `InputHandler` costs **1x per feature**. It keeps 4,480 lines of jest tests and the
  138 targeted adapter tests (`webview-coverage.md:17`) green throughout.
- The honest reasons to rewrite anyway:
  - busybox-shaped dispatch: a `find_range` table, `.` as recorded input, and `@` almost free.
  - An Edit-returning API instead of mutating a fake element.
  - A code-point offset model.
  - Removing prompt logging and the `innerHTML` undo.
  - Removing the visual-line model, which is spread through `dd`, `I`, `A`, `o` and paste (A10),
    not just motions.

  These are good reasons. The LOC table is not one of them: it miscounts `event-interceptor` and
  omits adapters and tests (A14).

**Recommended shape:** a *strangler on the existing seam*.
1. Freeze the contract extracted from the three working adapters (`snapshot`/`commit`/
   `stateSignature`).
2. Put the new engine behind it.
3. Switch adapters one at a time.

The plan's §6 already has the one-host-at-a-time rollout. Add step 0: "extract the contract from
the adapters and re-point them".

**C3. Is per-line metadata the right place for structure?** No. It is a half-measure.
- **Nested lists and quotes containing lists** need a *stack* per line (`[blockquote, list(depth
  2), item]`), not one `kind`.
- **Code blocks:** one block becomes many lines.
- **Hard break versus paragraph:** both are `\n` in flat text but differ for `J`, `dd` and `o`.
- **Atoms (mentions) are inline, not per-line.** They need a placeholder character (for example
  U+FFFC) with span metadata, so `x`, `w` and yank treat them as one unit. The PM adapter excludes
  them today (`webview-coverage.md:41`).
- **Markers:** `I` skipping a "rendered marker" is incoherent. In PM the marker is not in the text
  at all; in plain-text markdown (`- item`) vi semantics say `I` *does not* skip `-`.
- **Structural intent:** with text-only edits, the adapter must reverse-engineer "split list item"
  from an inserted `\n`.

**Alternative:** keep the engine flat, but let the engine emit a small set of **structural
intents** next to text edits (`openLine{after, inherit}`, `joinLines`, `deleteLines`). The adapter
maps each intent to a host command (`splitListItem`, …) or rejects it via the rollback path in §3.2.
Then `o` on a list item means "new sibling if the schema allows, else a plain line, else reject".
The adapter decides and validates. Ship v1 with PM's current rule: refuse takeover on
non-plain documents.

**C4. Is dropping `@` defensible?** Not on cost.
- busybox's `.` stuffs the recorded command into the input queue (`vi.c:4021-4028`). Once our `.`
  replays through the parser, `@x` is "feed `reg[x]` into the same queue" plus a recursion guard,
  roughly 15 lines.
- `@` is **easier than `.`** in our hosts: `@` executes register *text* (which the engine has),
  while `.` needs *captured* insert text (which it does not, risk 1).
- The `TINY` rule already admits nvi-only commands of this cost (`build_matrix.py:326`). `@` and
  `&` (about 5 lines once `:s` exists) are excluded by stale reasoning (`build_matrix.py:308,310`).

**Ruling:** if `.` is keystroke replay, `@` and `&` are in. Dropping `!` remains correct: it needs
a shell, and the daemon would become an RCE surface.

**C5. Is compare-and-swap enough, or is a merge needed?** CAS is the right *default*, but alone it
loses work.
- Long vim sessions in live chat apps will commonly see *some* change, much of it benign
  normalisation (§3.6).
- Minimum: compare normalised text; on mismatch, keep the vim result in `"e` plus the temp file,
  and report both.
- Cheap merge: the daemon already holds base (sent), ours (vim) and theirs (current). Run a 3-way
  merge with Python `difflib` or `git merge-file -p`, auto-apply when there are no conflicts, and
  otherwise fall back to the CAS refusal.
- Alternative to merging: ask the adapter to make the field read-only for the session. That is
  cheap on textarea and Monaco, and hard on PM and Slate.
